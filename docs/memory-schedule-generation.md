# Affine schedules through actual Loop generation

The unified guarded C compiler accepts affine schedules and generates the
actual candidate Loop from the extracted source. The fragment and complete
Csem-to-Asm theorems have compiled, and the extracted compiler has passed
complete-program acceptance and refusal tests.

The route is:

```text
actual C region → checked source description → source Loop → actual extraction
  → replace proposed schedules → PolCert CodeGen instantiated with CompCert Mem
  → normalize generated bounds → independently extract and check candidate
  → safe runtime condition + candidate/source selection → CompCert assembly
```

## Proposal interface

`GuardedScheduleCandidate schedules steps` carries one affine schedule per
source instruction and a list of candidate-to-source iterator maps. Every
schedule is a list of affine rows `(coefficients, constant)`. The proposer can
be a human, a heuristic or an external scheduling tool. It does not submit
replacement instructions, array identities or source domains through this
route.

`memory_generate_scheduled_loop` runs the actual source extractor, requires
the schedule count to match its instruction count, and retains the source's
domains, instructions, witnesses, argument transformations and accesses.
Short coefficient vectors are padded with zeros. Vectors longer than the
parameter-plus-iterator dimension are refused.

`MemoryCodeGen` instantiates the upstream `CodeGen` functor with the concrete
CompCert-memory IR. Its topological sort proposal is a concrete bounded
definition, limited to 256 nodes, and is still checked by the original
permutation and ordering checker. The native compiler extracts this definition
instead of replacing it with an external function. A generator alarm returns
no proposal. Each source instruction is generated separately to avoid the
expensive cross-statement geometric construction. Static schedule prefixes
order the instruction proposals; matching loop nests are fused only through
the dynamic affine prefix shared by all schedules. An ordinal-first schedule
keeps separate nests. The result is independently checked, including its
actual instruction order.
`memory_attempt_codegen_accept` proves that a returned candidate came from
an alarm-free generator result; an alarmed default is discarded.

## Independent checking

`memory_generated_affine_bounds` converts lower `max` and upper `min` bounds
to an enclosing affine range with tests in the body. It also removes generated
single-iteration loops by substituting their bound for the iterator, and
flattens sequence wrappers and empty sequences. It clears positive integer
division from comparisons into affine integer inequalities where possible. These steps remove the
otherwise spurious ordinal and coordinate-restoration loop dimensions. It is a proposal
normalizer. The complete C correctness theorem does not assume that this
normalizer or the proposed schedule is correct.

The resulting Loop goes through the existing mapped-candidate checker,
including both actual extractions, integer domain equivalence, argument and
access correspondence, and dependence preservation. It also goes through
the checked machine backend. The source range, width and physical-array
conditions are generated by the same existing guarded region path.

`check_memory_named_scheduled_region_sound` and
`check_memory_ragged_scheduled_region_sound` consume those candidate
certificates. The unified `compile_memory_unified_regions_correct` theorem
therefore covers the generated schedule route with the same projected
public-state relation and Csem-to-Asm composition.

## Native input

For the currently supported two-parameter, two-iterator source families,
the source extraction's point coordinates are `[M; N; i; j]`. This proposal
requests interchange and gives its candidate-to-source coordinate map:

```text
(schedule ((affine (0 0 0 1) 0)
           (affine (0 0 1 0) 0)
           ordinal)
          ((swap 0)))
```

The native parser expands `ordinal` to each instruction's static position.
`(ordinal factor bias)` represents `factor * position + bias`.
`schedule-list` instead accepts an explicit list of per-instruction
schedules. Both forms have size limits and remain untrusted.

The initial source recognizers retain their existing scope: bounded dynamic
rectangles and `j < i + M`, with the existing array operation forms. This
route does not add arbitrary C source recognition, neighboring accesses,
pointer slices or a Pluto connection. It connects actual affine schedules
to actual code generation and the guarded whole-program checker.

```sh
opam exec --root=/tmp/guard-opam --switch=guard -- make native-memory-schedules
```

## Validation

At commit `66222fb`, the proof audit recompiled 89 memory adapters and seven lowering
modules. Instruction proofs retain their seven inherited assumptions; the
validator retains twelve; the complete compiler retains exactly the 42-item
CompCert/validator union. No code-generation, normalization or sorting axiom
is added.

`build/native-memory-schedules/report.json` records thirteen configurations
for each source family. Each rectangular configuration compares 4,022 full
program output lines with GCC and an independent model; each nonrectangular
configuration compares 1,385. Identity, interchange, shifts and skews are
accepted in all ten rectangular and seven nonrectangular functions. Fission
is accepted in nine rectangular functions and all seven nonrectangular ones;
the dependent three-array region is refused. Incorrect maps, missing
schedules, oversized coefficients, resource exhaustion and invalid oracle
certificates produce no guarded replacement. Reverse statement order and
constant schedules are accepted only in two independent regions in each
family: read-only/copy regions for rectangles and pure-write/copy regions for
nonrectangular loops. The explicit three-site identity input is accepted
only where its statement count matches.

The same compiler also passed the existing 21-configuration nonrectangular
suite, including efficient division-based tiling and its fallback cases.
The older affine-map, multiarray and unified regression suites passed during
this change. These are bounded source families; general affine C bounds,
neighboring accesses, different layouts and pointer buffers remain in progress.

The subsequent [parametric affine-bound extension](memory-parametric-affine-bounds.md)
adds signed affine inner C bounds and arbitrary parameter-context lengths to
the same schedule and whole-program path. Its proof audit recompiles 107
memory adapters and seven lowering modules. The results above record the
original source grammar at `66222fb`; the newer grammar and its regressions
are documented separately.
