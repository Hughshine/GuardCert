# 同一数组的布局重映射与真实依赖

不同步长的读、写可以指向同一个 C 数组。例如：

```c
int A[240];
/* 初始化 A 和循环控制变量 */
for (; i < N; ++i) {
    K = 2*i + M - P;
    for (j = 0; j < K; ++j)
        A[i*20+j] = A[i*24+j];
}
```

`memory_copy_layout_descriptors` 在两个名称相同时只登记一个对象。语法证书要求这个对象的完整数组长度一致。数组的两个访问函数仍分别是 `20*i+j` 和 `24*i+j`，因此验证器可以看到读写落在同一个逻辑单元上时的依赖；不会将两个步长误当成两个互不别名的数组。

`memory_copy_layout_registry` 从真实源首个 load/store 构造这个登记表，证明名称唯一及检查所需的有效地址。`memory_copy_layout_point_execution` 证明同一对象登记后的具体 CompCert 内存执行与指令执行对应。源循环解码、前提编码、候选执行及公开计数器恢复继续接到 `compile_memory_unified_regions_correct` 的完整 Csem→Asm 端点。

## 为什么不能随意重排

取 `N=5, M=9, P=0`，初始 `A[x]=5*x+2`。原顺序中的 `(i,j)=(2,12)` 先读取 `A[60]` 并写入 `A[52]`，之后 `(3,0)` 才覆盖 `A[60]`。按 `2×3` tile 顺序执行则先覆盖 `A[60]`。实际结果分别为 `A[52]=302` 和 `A[52]=362`。

完整程序测试还包含反向步长及递减行宽：`A[i*24+j]=A[i*20+j]`，`K=M-2*i+P`。两种源的循环交换、`2×3`、`4×4` 和 `17×13` 分块各有实际结果不同的反例，保存在 native 报告中。保持字典顺序的调度和外层 tile 大小为 1 的分块则应通过同一个依赖验证器。

## 复现与范围

```sh
opam exec --root=/tmp/guard-opam --switch=guard -- make native-memory-layout-copy
```

fixture 为 `examples/native_memory_layout_copy.c`，独立源模型和 GCC 对照为 4,868 行完整输出，报告为 `build/native-memory-layout-copy/report.json`。测试核对接受与拒绝、实际快分支的两个步长、数组全部内容及公开出口。

在提交 `9ca9f80` 的本阶段完整审计通过：119 个适配模块和 7 个 lowering 模块，完整编译器假设并集仍为 42 项。15 组完整程序配置全部通过。保持顺序的四种调度和两种单行 tile 配置各接受八个支持的函数；循环交换及其余二维 tile 配置保留六个独立数组函数，并拒绝两个有实际依赖反例的同数组函数。错误映射、维度、系数、资源限制与无效证书配置全部回退。

本实例覆盖一条有符号整数复制、独立固定步长、稳定参数仿射内层上界，以及名称相同且长度一致的数组。任意不同布局混合语句列表、邻居偏移访问、指针切片和一般 C 仿射源仍需要更多具体源实例；一般指令 checker 的表达力不能代替这些源语义证明。
