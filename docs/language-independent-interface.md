# 语言无关接口：能力、使用方式与分类

本文面向要为自己的语言接入带动态条件变换的人。先固定入口检查与回退的接口，再说明哪些场景能使用它，哪些需要扩展判断或协议。日期为 2026-10-05。

本轮新增 [GuardInterface.v](../prototype/interface/GuardInterface.v) 与 [GuardInterfaceExamples.v](../prototype/interface/GuardInterfaceExamples.v)，作为接口 v1 的机械化原型。它们不依赖 CompCert。现有 CompCert 编译器仍使用旧接口；本轮不把新接口原型算作已完成的 CompCert 迁移或新的原生运行证据。

## 1. 框架提供的服务

给定源片段 `S`、候选 `T` 和一份条件性正确性证书，框架构造并证明：在实际入口安全执行检查，接受时运行候选，不接受时执行已证明安全的失败路径，最后将片段证明交给语言的上下文适配器。

```text
规则或候选 ── 条件性局部证书 ── 入口前提 P
                                  │
                         编码、静态消解、检查生成
                                  │
                         检查代码与检查证书 G
                                  │
                     检查 → 候选 / 已证明的回退
                                  │
                      局部证明 → 上下文 → 完整程序
```

这里有两个不同的服务。组合核心消费检查与变换证书，自动得到 guarded 片段的正确性。条件处理服务则从受支持的前提 AST 生成检查及证书。前提发现器可以再从一对源／候选提议 AST，但它需要自己的可靠验证流程。只有组合核心不意味着已经实现任意候选的条件发现。

“语言无关”意味着框架不解释整数、地址、类型、SQL 值或代码版本。语言实例提供这些事实及其检查；核心只使用事实之间的证明和执行契约。一个语言若没有某项可实现检查，可以提供静态证据、可靠的充分检查或 unknown，不必实现完整判定器。

v1 的默认目标是单次执行的行为精化：每一种目标观察，都有满足指定关系的源观察。另有独立的 preservation 接口，用于匹配每一种源观察。等价可以要求两者。候选产生器可以完全不受信任，但证书必须绑定实际源、候选和检查代码。

## 2. 四份核心契约

| 契约 | 提供者 | 内容 | 框架消费它后做什么 |
| --- | --- | --- | --- |
| `guard_host` | 语言／IR 适配器作者 | 状态、代码、观察、执行关系、检查执行、安全性质和分派构造器的精确语义 | 用语言的构造器生成带检查的代码 |
| `guard_certificate` | 已验证检查生成器或检查作者 | 插入域、检查安全、可执行性、所有检查结果的可靠性、成功／拒绝后的状态关系 | 建立候选前提，约束检查产生的状态变化 |
| `conditional_certificate` | 规则作者或已验证候选检查器 | 源、候选、回退，以及两条分支从检查后状态到原入口源行为的精化 | 得到整个 guarded 片段的局部精化 |
| `context_certificate` | 语言的宿主适配器作者 | 合法插入点、入口域证明、实际代码绑定、上下文对局部关系的兼容性 | 将局部精化提升到其支持的完整程序 |

规则使用者通常不写这四份证明。已有语言适配器、性质库和规则库之后，他们提供代码与候选，执行证书构造和安装流程。新增性质时证明一次原子语义与检查；新增规则时证明一次条件性局部正确性；新增语言时才承担语言和上下文适配。

### 2.1 语言提供什么

核心形状为：

```text
State, Code, Observation, Check
run       : Code × State × Observation → Prop
check_run : Check × State × AcceptBool × State → Prop
check_safe: Check × State → Prop
select    : Check × Code × Code → Code
```

`select` 可以是 `if`，也可以先执行一段检查语句再分派。语言证明精确的分派契约：

```text
run(select(g,T,F), s, o)
  ↔ ∃ b,t. check_run(g,s,b,t) ∧ run(if b then T else F,t,o)
```

它既有引入方向，也有消解方向，排除没有对应检查／分支执行的额外目标观察。若检查可能发出事件，该契约必须在语言真实观察中证明；不能通过删除这些事件来声称保持了轨迹。入口回退的默认实例要求检查在所选观察中没有额外公开效果。

`Observation` 必须说明包括什么：值、公开状态、内存、退出种类、事件轨迹，或者完整行为。只建模正常终止端点，就只得到端点定理。声称覆盖发散、异常或错误时，必须在语言语义及宿主适配中覆盖它们。

`check_safe` 的意义也由语言正式定义：例如所有检查执行无故障、有限完成、读取有权限、只写私有状态。语言适配器必须将这项性质连接到它的实际执行语义。不能把它定义为一个无依据的 `True` 来声称检查安全。原型的数学函数语言没有故障或发散构造，检查本来就是返回有限结果的全函数。

### 2.2 三种状态与前提的时点

区分原入口 `s`、检查后状态 `t`、分支执行后的观察 `o`。v1 的逻辑前提 `P(s)` 固定在原入口，候选实际在 `t` 上执行。检查证书提供：

```text
D(s) ⇒ 检查安全，且存在一次检查执行
∀ check_run(g,s,b,t), D(s) ⇒
  b=true  时：P(s) ∧ AcceptedEntry(s,t)
  b=false 时：RefusedEntry(s,t)
```

可靠性量化所有检查执行；可执行性只是存在性。对非确定语言，“存在一条完成路径”不能代替所有路径的终止、安全或公平性证明，这些要在 `check_safe` 及语义适配中声明。

`D` 是宿主必须建立的检查／插入域，不是未经验证的优化假设。`P` 是运行时接受所建立的变换前提。把 `P` 塞进 `D` 后省略动态证明，会把有条件变换偷换成条件已知的变换。

成功和拒绝可以有不同的状态关系。例如成功保留候选所需缓存，拒绝清理 scratch 或恢复源入口。关系可以保持公开值、描述内存对应或保存某份快照，不要求整个状态相等。

### 2.3 规则提供什么

条件性证书绑定实际 `S,T,F`，其中 `F` 是失败路径：

```text
D(s) ∧ P(s) ∧ AcceptedEntry(s,t) ∧ run(T,t,oT)
  ⇒ ∃ oS. run(S,s,oS) ∧ R(oT,oS)

D(s) ∧ RefusedEntry(s,t) ∧ run(F,t,oT)
  ⇒ ∃ oS. run(S,s,oS) ∧ R(oT,oS)
```

最简单的 `F=S` 也需要状态运输证明，因为检查已经执行过。检查消耗了公开值、修改了内存或产生了外部效果时，不能仅凭代码文本相同就认定回退正确。

候选原有局部定理若比较同一状态上的 `S,T`，适配器可以使用 frame／表示关系把它转换为上述入口锚定证书。这个转换是可复用库的一部分。核心没有要求每条规则重证检查过程，也没有自动提供任意 frame 的运输定理。

原型的 `framed_rule_certificate` 已提供一种转换：实例证明检查后的源观察能运输回原入口，且成功关系保持域与前提；规则作者只需给同状态上的局部精化。该辅助定理要求源观察精确运输；更一般的表示对应仍使用完整条件性证书或另外的关系组合证明。

### 2.4 上下文提供什么

宿主声明合法位置及组合规律：

```text
LegalPlacement(C,S,D) ∧ AdmissibleReplacement(C,S,T,D)
  ∧ LocalRefinement_D(T,S,R)
  ⇒ ProgramRefinement(plug(C,T),plug(C,S),R_program)
```

这里的 `C` 包括实际外围代码及其需要的环境。语言适配器负责 live-out、控制出口、调用、标签／多入口、异常以及所覆盖执行的进展。局部关系 `R` 能被哪些 continuation 消费，也是宿主的证明责任。

框架随后消费这份规律完成组合。它不会从最终值相等自动推出任意上下文相等，也不会从一个 terminating big-step 端点自动推出完整小步仿真。

目标侧的 `AdmissibleReplacement` 单独核对类型、私有状态新鲜性、入口／标签、退出及该宿主所需的进展。某些语言中它可由代码类型自动满足；使用端点关系连接小步宿主时，它可能包含非平凡的模拟协议。不能只检查源位置合法，就默认任意目标片段都可安装。

## 3. 前提到检查：固定证书链

```text
语义义务 Q
  ← 入口推导：静态事实 F ∧ 入口条件 A ⇒ Q
  ← 前提编码：Meaning(P) ⇒ A，或更强的双向对应
  ← 静态消解：F ∧ Meaning(P_residual) ⇒ Meaning(P)
  ← 检查编译：Accept(G) ⇒ Meaning(P_residual)
```

这四步分别交付证书。可执行生成器操作有限 AST；语义义务可以比 AST 更宽。框架不承诺从任意 `Prop` 生成程序。

现有 `formula` 支持常量、原子、合取、析取、否定；`property_dimension` 为每类原子提供命题及有证据的 `option bool` 决策。v1 保留这一表达核心。类型化的运算、量词、可读取的字段、快照及检查成本属于性质库与检查生成器。

| 检查结果 | 逻辑证据 | 在最终入口分派中的使用 |
| --- | --- | --- |
| `Some true` | 前提成立 | 可以接受 |
| `Some false` | 前提不成立 | 拒绝；在公式内部可作为否定证据 |
| `None` | 未取得正／负证据 | 保守拒绝；不能经否定变成接受 |

只有正向可靠的检查应把拒绝映射为 `None`。最终 AcceptBool 只是是否已经建立足够证据；它的 false 不意味着 `¬P`。SQL 的 NULL、语言的异常和框架的 unknown 也不是同一件事。

静态消解可以改变接受覆盖。例如静态证书证明某原子为真，即使动态检查只能返回 unknown，也可消掉这项检查。默认要求保持前提的可靠性，不默认要求新旧检查 Bool 精确相同；若要精确相同，应另给等价证书。

原子有求值前置条件时，应由检查生成器安排支配／短路关系，并证明沿每条实际路径安全。例如读取 `p` 指向的数据不仅需要非空，还需要相应访问能力；不存在一枚跨语言通用的“可读指针”机器测试。能力可以来自源执行、静态证明或经过建模的 runtime metadata。

检查若改变了后续检查读取的状态，需要保存入口快照、证明性质稳定，或者重新建立证据。把两个单独安全的检查合起来，不自动得到安全且含义相同的合取。

## 4. 按六个独立维度分类

不能仅按 overflow、alias 分类。这些是前提库的类别；同一 alias 条件，在入口交换和执行到一半的去优化中需要不同协议。

### 4.1 要保证什么

| 判断 | 规则证书的目标 | v1 的适用方式 |
| --- | --- | --- |
| 精化 | 每种目标行为都有允许的源行为 | 核心默认定理；必须明确 UB、异常和发散的语义 |
| 等价 | 两边互相匹配行为 | 同时提供 refinement 与 preservation，并证明所需关系性质 |
| 近似／误差 | 指定误差关系和输入域 | 一次局部关系可用 `R` 表示；跨上下文和多次变换需要预算组合证明 |
| 修复／功能更新 | 新规格及未影响域的保持 | 需要变化契约或规格判断；与旧程序精化通常不足以证明修复 |
| 插桩／enforcement | 策略满足、允许干预、合法执行透明性 | 需要策略与事件判断，不能默认使用等轨迹 |
| 信息流／constant-time | 两次或多次执行的观测关系 | 需要关系式／product 语义及 guard 泄漏义务；单执行证书不足 |

任意 `R` 不是免费支持任意正确性目标。原型的 theorem 仍是一次源／目标行为对应；超性质、预算及变化契约需要各自的组合规律。判断扩展必须交付 guard 组合与上下文组合定理，不能只给一个可填写的 record。

### 4.2 前提何时建立、有效多久

| 时点／寿命 | 例子 | 额外义务 |
| --- | --- | --- |
| 静态、链接／装载时 | 类型事实、代码版本、CPU 能力 | 证据适用于当前配置，且直到消费时仍有效 |
| 片段入口 | 值域、数组窗口、参数 shape | 入口条件足以支持整个候选；不要求 `P` 永远保持，除非局部证明需要 |
| 每次调用／迭代 | 函数身份、对象布局、局部依赖 | 每次消费前重新检查，或证明前次证据稳定 |
| 提前检查／缓存 | 循环外检查、证据复用 | 从检查点到使用点的依赖不变、失效规则、版本／ownership 依据 |
| 内部检查点 | JIT 去优化、逐步特化 | 当前位置状态与源 continuation 的恢复对应 |
| 持续监控 | 事务、事件政策、并发干扰 | 历史、环境变化、原子性及监控反应语义 |

“检查成功时成立”不意味着“稍后使用时成立”。入口前提也不能直接描述尚未取得的未来值；需要推导、快照、内部 guard 或一个能覆盖未来执行的静态证明。

### 4.3 检查能有什么效果

| 效果 | 能否使用入口核心 | 要证明什么 |
| --- | --- | --- |
| 纯计算 | 可以 | 类型、定义性、结果解释，实际分派没有额外行为 |
| 只读源状态／内存 | 可以 | 读取权限、执行路径和读取时间；不得提前触发源不会触发的错误 |
| 修改私有 scratch | 可以 | 成功／拒绝的 entry relation、公开观察运输、freshness |
| 私有分配或表示准备 | 取决于宿主 | 内存对应、别名可见性、清理和资源语义；分配失败要有协议 |
| 公开写入、I/O、异常 | 默认核心不直接覆盖 | 将 effects 纳入真实观察及组合规律，或证明它们可恢复／被允许 |
| 并发读取或同步 | 需要并发适配 | 检查与消费间的干扰、线性化／ownership、内存模型 |

若语言观察包括资源耗尽或时间，私有分配和额外检查也可能可见。当前顺序功能正确性的观察选择不能自动给出这些保证。

### 4.4 失败后做什么

| 协议 | 最小证书 | 与 v1 的关系 |
| --- | --- | --- |
| 编译期不应用 | 返回原代码及绑定证明 | 候选检查器的拒绝路径，不是运行时否定证据 |
| 原入口回退 | 检查后状态可继续运行源，且行为对应原入口 | v1 默认；失败路径可包含恢复或清理代码 |
| 选择另一版本 | 当前状态可安全尝试下一份 guard | 需要域稳定和证据／状态运输；可用每层证书组合 |
| 检查点去优化 | 已执行前缀与当前位置、堆及活动 continuation 的对应 | 新的 checkpoint 协议；不能重跑源入口撤销外部效果 |
| 中止／重试 | 所有前缀对外可接受，回滚及重试规则正确 | 事务／历史协议，不等于入口回退 |
| 报错／blame | 错误是所选规格允许的结果 | 新判断或允许错误的观察关系；不是默认行为保持 |
| 修正／迁移 | 变化范围、状态转换和新规格 | 专用变化协议与宿主证明 |

v1 允许失败代码 `F` 与 `S` 不同，但仍要求从原入口得到源行为对应。这能容纳检查前的私有恢复，不能据此声称已支持执行到一半的 deoptimization。

### 4.5 前提怎样得到

| 来源 | 用户输入 | 系统责任 |
| --- | --- | --- |
| 已知规则 | source/target 模式及 `P`、局部证明 | 实例绑定、编码、残留检查、安装 |
| 带 witness 的算法 | 候选、依赖／域／重排证据 | 可靠静态检查，导出尚需动态成立的义务 |
| 人工或工具独立候选 | `S,T`、允许观察与条件域 | 在受限域寻找并验证条件；不支持时拒绝 |
| 用户提交 guard | `S,T,G` 及可选 hints | 验证接受含义、执行安全、状态影响和分支证明 |
| 外部证据／缓存 | token、metadata、事实依赖 | 验证来源、绑定、寿命和消费条件 |

所有来源在四份核心契约处汇合。候选发现的测试、求解器结果和 witness 都不自动成为 Rocq 证明；需要已证明的 checker 或明确的可信前提。

### 4.6 片段怎样与程序连接

| 片段 | 语言适配器要增加什么 |
| --- | --- |
| 表达式 | 类型／值保持、求值顺序、严格或短路上下文的区别 |
| 有限语句区 | 状态、退出种类、live-out、正常完成的进展 |
| 循环／调用 | 内部步骤、发散、调用环境与 continuation，或者明确受限的终止域 |
| 多入口 CFG | 每个入口的条件和对应；或验证不存在绕过 guard 的入口 |
| 异常／非局部退出 | 异常栈、控制出口与清理行为对应 |
| 不同 IR／表示 | source/target 状态关系、目标中的源 fallback 实现及 lowering 证明 |
| 并发或开放模块 | 环境干扰、外部调用、ownership 和模块上下文兼容性 |

v1 的候选与失败代码位于同一个宿主。跨 IR 的源可以先通过已证明 lowering 得到宿主源及其合同，或者增加异质状态的接口；仅把两个 Code 类型改成不同名字尚不构成跨语言支持。

## 5. 前提库按表达与证据分类

| 维度 | 原子应绑定的信息 | 可执行／静态依据 | 不能默认成立的事 |
| --- | --- | --- | --- |
| 整数与位向量 | 位宽、符号、运算树、所需中间值和时点 | 已验证 checked arithmetic、宽化运算、范围证书、语言暴露的 flags | 无回绕不是一个全程序开关；检查自身也要安全 |
| 运算定义性 | 除数、移位范围、类型、源求值路径 | 支配事实与安全原语 | 源未到达表达式时，也不能擅自提前读取操作数 |
| 内存分离 | 地址 provenance、访问尺寸、读／写效果 | 实际地址比较、静态足迹或已建模 metadata | 基址不等不一定表示字节区间不重叠；只读别名可采用不同前提 |
| 权限与生命周期 | 对象身份、访问权限、ownership、生命周期 | 源执行能力、静态逻辑、受验证 token | NonAlias 不等于可读／可写；成功后仍可能失效 |
| 值稳定与缓存 | 被读值及其依赖、作用域、快照时点 | frame、无相关写入、版本或同步协议 | 入口事实不能无条件穿越 store 或调用 |
| 形状／索引域 | 边界、维数、布局、活动点、量词域 | 仿射证书、有限扫描、已证明的入口投影 | 静态盒中的地址不一定是源实际使用或有权限的地址 |
| 代码身份与表示 | 环境、函数／closure 身份、对象布局、版本 | 有语义的身份测试、类型证书和版本绑定 | 身份相同不能自动推出环境及表示条件相同 |
| 浮点与数值规格 | NaN、无穷、signed zero、舍入模式、误差预算 | 精确原语与范围／误差证书 | 实数恒等式不是机器位级等价；误差不自动穿越任意上下文 |
| 查询／领域不变量 | NULL、keys、bag multiplicity、schema／快照 | 元数据证书或有语义的运行检查 | 领域的未知值不能与检查器 unknown 混同 |
| 历史与并发 | 事件前缀、版本、环境干扰、公共输入关系 | monitor、ownership、关系式或历史证据 | 一个顺序状态 Bool 不自动表达历史策略或超性质 |

这张表规定库的职责，不声称这些库都已实现。核心的 Atom 是开放类型；某个实例支持哪些构造，必须由其检查生成器的支持清单确定。

有限的全称／存在条件可以提供生成器，例如遍历源实际访问。一般量词、可达性、未来终止性不能要求一个完整入口判定器。采样也不能代替遍历得到普遍分离结论；若允许误判概率，必须使用概率规格和相应判断。

对于 overflow flag，语言实例需要建模实际 flag 的设置、读取、清除及可见性，并证明它对应哪次计算。核心不要求所有语言有这种 flag；也不假设“当前 flag 为零”就证明候选将要进行的任意计算无溢出。宽化重算、静态区间和硬件 flag 可以作为同一语义性质的不同检查实现。

## 6. 使用者怎样接入

### 6.1 新语言作者的工作

1. 定义实际观察及正确性目标，明确是否覆盖错误、异常和发散。
2. 实现 `guard_host`：安全性质和分派契约必须对应语言真实执行。
3. 实现至少一种 `context_certificate`，声明支持的片段、入口、退出和状态关系。
4. 提供所需性质库及其实际检查原语。证明性质如何支持局部变换，例如某种物理访问分离与事件独立性足以交换两条指令。
5. 用非空执行验证检查可接受、可回退，并报告不支持的语法和入口域。

一次语言接入可以只支持一种片段形态。扩展到调用、异常或并发时，需要扩展宿主证明；不必因此把整数或内存解释加回组合核心。

### 6.2 新规则作者的工作

规则作者提供模式 `S,T`、义务 `Q`、可表达前提 `P`、编码／入口推导证书及条件性局部证明。已有检查编译器给出 `G`，frame 适配库转换局部定理，核心组合得到 guarded 合同，宿主安装。

```text
register_rule(pattern, obligation, premise_ast,
              encoding_certificate, conditional_certificate)

instantiate(actual_source)
  → NotApplicable(reason, actual_source)
  | Certified(target_code, local_contract, placement_contract)
```

这是使用层的概念签名；各语言的模式识别与证书构造函数可不同。`NotApplicable` 保留源，不解释成前提为假。规则库中的“原片段”必须是实际匹配的代码，不只是一个摘要或字符串名称。

### 6.3 只提供独立候选的使用者

使用者提供 `S,T`、片段接口、希望保持的观察及允许的条件域。条件化服务尝试构造局部证书与检查证书，成功后走同一安装链。分析器可使用测试、抽象解释、求解器或重排 witness 作为 hints；可靠性来自最后消费的证书。

默认不保证一定找到条件、条件最弱、接受最多或检查最便宜。永远拒绝也能满足可靠性，因此实用验收另外记录非空接受域、检查成本、候选成本及回退成本。需要强制候选可达的服务可以增加独立的 coverage certificate，但这不是正确性定理的隐含结论。

## 7. 四个端到端例子

### 条件算术取消

`S=(x*y)/y`，`T=x`。规则作者证明 `y≠0` 与指定机器乘积无回绕足以支持替换。性质库声明位宽、符号和运算树，检查生成器使用已证明安全的宽化运算。语言宿主证明操作数在插入点已定义，并将局部值合同放入其支持的表达式上下文。核心不解释乘法或 overflow。

源短路使表达式不可达时，宿主不能把 guard 提前放到会读未定义变量的位置。生成器只负责已声明入口域内的安全检查，不能替宿主猜测求值顺序。

### 指令或循环重排

`S` 是原顺序，`T` 是候选顺序。实例提供实际读写效果及“特定分离事实足以可交换”的定理；静态验证器检查重排／依赖 witness，检查生成器建立尚需运行时满足的事实。候选与回退在检查后的状态执行，再与原入口源行为对应。

非别名并不在所有语言中自动意味着可交换，例如可观察事件也可能限制次序。这项语义定理由语言实例负责。多面体算法只是产生／验证条件性证书的一种来源。

### 对象或函数特化

`S` 为通用调用，`T` 为已知实现。前提可以同时涉及函数身份、closure 环境、布局和代码版本；状态接口须能解释相关环境。检查原语证明身份与布局读取安全，局部定理覆盖调用行为及异常，宿主覆盖调用 continuation。缓存这些事实时另有失效或稳定性证明。

这是接口允许表达的场景，不是当前原型已提供的特化 pass。没有相应性质库和调用宿主时，安装返回不适用。

### 恒不接受与死候选

`P=False`，检查恒不接受，`T` 可以是任意代码。成功分支的局部义务由矛盾消去，失败分支仍需状态运输及源行为证明。原型的 `dead_candidate_refinement` 实际证明这一情况。它验证接口如何处理不可达分支，不作为有用接受覆盖或性能结果。

如果所谓“恒不接受”其实是某个原子求值失败，公式内部应保留 unknown。`unknown_under_negation` 验证 unknown 的否定仍不接受。

## 8. 检查生成器与证据组合的约定

检查生成器的使用层接口为：

```text
compile_check(atom_library, static_facts, premise_ast, entry_interface)
  → Unsupported(reason)
  | (check_code, guard_certificate)
```

原子库提供实际求值前置条件、正／负证据、允许效果及状态关系；生成器安排支配、短路、临时变量与结果分派，并证明整段检查的证书。提取后可以擦除证明，不要求运行时构造 Rocq proof term。前提类型可开放，具体生成器仍有有限支持范围。

当前纯原子公式编译器已在 `AbstractGuard` 中机械化。新的四契约原型接受完整检查代码及证书；没有新增一个自动处理任意有状态原子、任意效果的公式编译器。后续如要统一这部分，需使用入口快照和稳定性／失效信息证明组合，不能把纯编译器的状态不变假设直接删掉。

组合需要以下证据：

| 组合 | 应当固定的义务 |
| --- | --- |
| 合取／析取／否定 | 保持三种证据与实际求值顺序；后一个检查有权限且不破坏先前事实 |
| 静态消解 | 静态事实绑定插入点；残留前提足够；删除检查不会破坏所需的辅助状态或观察 |
| 多性质库 | 各库共享相容的入口 view 与状态关系；类型和证据解释不冲突 |
| 多候选版本 | 前次拒绝后的状态满足下次域；最终回退正确；每层检查证据仍有效 |
| 多阶段变换 | 中间代码真实绑定；各阶段关系可传递或可组合；阶段前提需适当运输／投影 |
| 缓存／提前检查 | 事实依赖直到消费点稳定，或按可靠失效规则重新检查 |

成本、最大接受覆盖和最弱条件是可以增加的质量证书。正确性接口不默认提供它们；生成器也应在报告中区分“缺少支持”“条件已证伪”和“保守未知”。

## 9. 对现有代码的映射与迁移

| 当前模块 | 对应 v1 的职责 | 迁移需要核对什么 |
| --- | --- | --- |
| `AbstractGuard.language` | 无状态变化的 `guard_host` 特例 | 复用双向 `conditional_spec`，检查后状态等于入口 |
| `SemanticFacts.property_dimension` | 命题原子与三种证据 | 保留正／负／unknown 区分及解释正确性 |
| `AbstractGuard.compile_condition` | 纯原子公式检查生成 | 复用精确短路分派；域与实际安全原语仍由实例提供 |
| `StatefulGuard` | 带私有状态的入口协议 | 增加目标行为消解／refinement；旧 introduction 与 preservation 不足以推出它 |
| `AffineNestFlagLanguage` 与区域证明 | 实际检查、frame、局部候选及宿主连接 | 核对原入口前提、所有检查结果、安全性质和目标 admissibility |
| 各 Clight 宿主 | `context_certificate` | 保留其实际小步、进展、标签、live-out 和类型义务，不能只套端点合同 |

迁移采用新接口消费旧实例定理的方式。旧证明可以继续存在；共享核心不得引入整数、指针或循环 syntax 依赖。没有迁移完成之前，不能声称现有 CompCert 编译器已通过新接口。

独立复现：

```sh
opam exec --root=/tmp/guard-opam --switch=guard -- make interface-proof
```

报告在 `build/interface/report.json`，编译日志在 `build/interface/proof.log`。本轮编译两个新接口模块并重编译一个既有依赖；九个新打印端点均为闭合证明。实例包括私有 scratch、接受、回退、任意死候选、unknown 否定、完整数学函数上下文，以及 preservation 允许额外目标结果的反例。这个“完整程序”是明确建模的小函数语言，不是新增 CompCert C→Asm 验证。

## 10. v1 固定哪些边界

固定入口锚定、显式插入域、所有检查结果的可靠性、独立安全性质、成功／拒绝状态关系、实际 source/target/fallback 绑定、refinement 与 preservation 的区别、宿主目标 admissibility。原子库、条件域、候选产生器、观察与状态解释保持可替换。

入口回退作为第一份可用协议；判断扩展和检查点恢复作为单独模块。后续模块必须交付具体生成／验证算法、局部组合规律和宿主组合证明。给出一个任意 `Prop` 字段不是支持新场景的验收标准。

接口实用验收需要同时回答：用户是否能使用现成适配器；新增性质／规则各要证明多少；检查是否有非空接受域；未支持构造怎样拒绝；有哪些观察与上下文被证明覆盖。这些问题与算法成本和论文新颖性分别报告。
