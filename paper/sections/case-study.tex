\section{CompCert Case Study: Optimistic Affine Loops}
\label{sec:case-study}

The case study tests the interfaces against real Clight execution and memory.
PolCert supplies a capability reference for affine domains, candidate schedules,
and tiling; the integration uses GuardCert's own source/guard adapters together
with the existing vendored optimizer proof infrastructure. The concrete toolchain
is pinned to CompCert~3.18, Rocq~9.2, and Stdlib~9.2.

\subsection{Established Compiler Path}

The current complete path supports a loaded signed root bound with a constant
offset and canonical affine descendants. It captures the initial header word,
executes private numeric and memory checks, validates an untrusted candidate,
and retains the original source on refusal. Candidates include schedule
reordering and supported tiling/domain witnesses; successful checking binds the
candidate to the actual source description.

For this path, \code{compile_offset_affine_multi_regions_correct} proves that a
successful compiler result is related to the original Csem program by a
backward simulation into CompCert assembly semantics. The proof composes
SimplExpr, SimplLocals, the expression-region host, and the verified backend.
The region contracts and host progress obligations determine the source class;
the theorem is not a license to install arbitrary Clight fragments.

\paragraph{Candidate production and the connected affine successor.}
The earlier native routes propose a candidate Loop AST through built-in
policies or external input. They use PolCert extraction and polyhedral
correspondence/dependence validation before concrete lowering and guarded
installation. The memory instance's external scheduler and phase-export hooks
still refuse; the older prepared optimizer adapter is proved separately but is
not called by those C drivers. These results establish conditional candidate
validation, not an installed automatic scheduling/code-generation pipeline.

The selected frontend now uses paired \code{\#pragma}\ \code{scop} and
\code{\#pragma}\ \code{endscop} markers. It records fresh label identities
before elaboration and retains them through normalization. The new Clight host
restricts discovery and installation to selected occurrences; filtering a
structural AST table alone could otherwise rewrite an identical unmarked loop.
It proves identity on unselected subtrees and a whole-program simulation under
the existing region, progress and resource contracts. The resulting compiler
endpoint, \code{compile_selected_tensor_literal_regions_correct}, composes to
Csem-to-Asm while reusing the literal tensor guard and candidate validation.
The native metadata pass lies at the parser/elaborator boundary; this is not a
new verified Cabs-to-Cabs pass. Direct declarations in a marked span refuse
selection so a new surrounding block cannot shorten their scope. Malformed
marker pairs also preserve their whole original function.

A marker requests an attempt and supplies no semantic assumption. A connected
successor now exports the checked family's canonical source model, invokes
Pluto on OpenScop, imports and validates the affine schedule, and calls
PolCert's proved prepared code generator. The installed candidate Loop comes
from that generator. The final existing mapped-domain factory rechecks it and
supplies forward execution and progress; the selected compiler's theorem
already permits an arbitrary data-only proposer. Source, scheduled model,
generated Loop and phase receipts are retained alongside actual Clight output.

Pluto retains the original order on the evaluated tensor examples. A further
untrusted layout phase reads the affine WRITE matrix and proposes traversal in
logical coordinate order: a column-order address yields a nonidentity
$(j,i,k)$ schedule. This phase constructs a scattering matrix, rather than
target Loop code; the same validator, prepared codegen and final factory check
its result. The generic kernel is unchanged, while the domain supplies the
model/transition obligations and the language host supplies installation.

Two new bridge theorems map completed generated execution back to the source
model and source Loop. They are backward correspondence results; they do not
replace the factory's progress proof. The route reuses compatible extractor,
affine-validator and prepared-codegen components, rather than literally calling
the frozen older \code{Opt_prepared} objects. Strengthening and combined
loaded-header/dynamic-layout integration remain pending.

A tiled successor carries the actual proposed Loop and point-space witness
data, rather than reconstructing a fixed target from tile sizes. It validates
the affine and tiling phases and runs prepared codegen on the transformed
point space. An actual C probe exposed a further boundary: codegen emits
\code{min/max/floordiv} bounds, while the source extractor accepts affine bounds.
An untrusted adapter keeps the generated loop skeleton and instruction arguments,
proposes affine enclosing bounds, and adds affine membership guards. For positive
$d$, it encodes $q<\lfloor e/d\rfloor$ as $d(q+1)\leq e$.
The final checker validates the adapted candidate's complete correspondence with
the assumed source; it trusts neither the proposed bounds nor that identity.
Both raw and adapted Loop outputs are retained. No separate raw-to-adapted
equivalence theorem is claimed. The codegen backward theorem concerns the raw
output; the installed candidate obtains forward execution and public-exit
restoration from its own checked certificate. The same guard encoding and
selected-region language host are reused, with an unchanged generic kernel.

\subsection{Nested Loaded Bounds and Actual Candidate Execution}

An adapted Figure~2 source from OLO~\cite{olo2017} supplies the concrete
source for the new nested compiler:
\begin{lstlisting}[language=C]
for (row = 0; row < shape[0] + 1; row++)
  for (column = 0; column < shape[1] + 1; column++)
    for (component = 0; component < 5; component++)
      output[(row * 16 + column) * 5 + component] =
          row + column + component;
\end{lstlisting}
This preserves the three-level control pattern and two repeatedly loaded
headers. It uses a flat fixed layout and an arithmetic store body; it is not
the full NAS BT kernel. The output may alias either header. A store can then
change the next source test, so the captured iteration domain need not describe
the original execution until preservation has been established.

header only if the actual outer test is active. An empty outer loop therefore
requires neither a defined child counter nor a readable second header. The
source's modular \code{Int.add} computation is kept distinct from the raw memory
observation; no-wrap facts belong to the accepted modeling condition.

by the source. It transports access permissions back to the guard-entry memory,
not loaded data values. Each accepted body check must protect \emph{all} captured
observations before the next child test is justified. Completion of those checks
for the current row permits the next outer test. Only after this preservation
chain can the proof derive execution of the cached source and consume the
affine candidate certificate.
